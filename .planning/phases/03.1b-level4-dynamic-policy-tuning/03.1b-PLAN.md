# Phase 3.1b Plan: Level 4 Dynamic Policy Tuning

<objective>
Improve the Phase 3.1 Level 4 amount-bin dynamic policy by reducing over-blocking on Cost-A and Cost-B while preserving the strong Cost-C result. The phase adds validation-only candidate tuning over existing Phase 2 risk scores and Phase 3.1 outputs. It does not train a new supervised model, does not implement Level 5, and does not tune on test.
</objective>

## Why This Phase Exists

Phase 3.1 produced the first useful dynamic-policy signal:

- Level 4 is strong in Cost-C, where FN is heavily penalized.
- Level 4 improves fraud recall.
- Level 4 can over-block in Cost-A/B, causing precision and FP Cost to degrade.

Phase 3.1b exists to make Level 4 more defensible before adding MiniLM hybrid logic in Phase 3.2.

## Scope

### MVP

- Create `notebooks/04b_dynamic_policy_tuning.ipynb`.
- Reuse the same `RUN_MODE` ladder:
  - `smoke`

- Implement a candidate grid for tuned Level 4 policies:
  - original amount-bin threshold policy;
  - shrinkage-to-global thresholds;
  - precision-guard thresholds;
  - alternate amount-bin strategies.
- Select candidate policies using validation only.
- Apply frozen selected candidates to test.
- Save tuned Level 4 outputs separately from Phase 3.1 outputs.

### Stretch Goal

- Add a diagnostic expected-cost policy with a modified FP cost:

```text
C_FP = fixed_review_cost + alpha * TransactionAmt
```

This must be labeled as `diagnostic_modified_cost_model`, not as the original reward formula.

- Add a robust selector that optimizes Cost-C while bounding Cost-A/B degradation.
- Add disagreement analysis between Phase 3.1 Level 4 and Phase 3.1b tuned Level 4.

### Out of Scope

- No Level 5 MiniLM-assisted hybrid policy.
- No Q-bandit/RL retraining.
- No new LightGBM/XGBoost training.
- No PPO/A2C.
- No test-set tuning.
- No claim that `TransactionAmt` makes the original closed-form expected-cost threshold dynamic.

## Candidate Policies

### Candidate 0: Phase 3.1 Level 4 Reference

Use the exact Level 4 thresholds from Phase 3.1 as the reference row:

```text
policy = level4_amount_bin_dynamic_threshold
```

This is not reselected; it is the comparison anchor.

### Candidate 1: Shrunk Amount-Bin Threshold

Goal: reduce aggressive per-bin thresholds that create too many false positives.

For each cost config and amount bin:

```text
threshold_final = lambda * threshold_bin + (1 - lambda) * threshold_global
```

Validation grid:

```python
LAMBDA_GRID = [0.00, 0.25, 0.50, 0.75, 1.00]
```

Interpretation:

- `lambda=1.00`: original Level 4 amount-bin threshold.
- `lambda=0.00`: Level 3 global threshold.
- Middle values allow smoother amount-bin behavior.

Policy name:

```text
level4_shrunk_amount_bin_threshold
```

### Candidate 2: Precision-Guard Amount-Bin Threshold

Goal: prevent precision collapse in Cost-A/B.

For each cost config and amount bin:

1. Evaluate the same threshold grid on validation.
2. Keep thresholds satisfying a guard such as:

```text
precision_fraud >= precision_floor
```

or:

```text
fp_cost <= fp_cost_cap_multiplier * fp_cost_global_in_bin
```

Recommended grid:

```python
PRECISION_FLOOR_GRID = [0.05, 0.10, 0.15, 0.20]
FP_COST_CAP_MULTIPLIER_GRID = [1.00, 1.25, 1.50, 2.00]
```

If no threshold satisfies the guard:

- fall back to the global Level 3 threshold for that bin;
- record `fallback_used=True` and `fallback_reason`.

Policy name:

```text
level4_precision_guard_threshold
```

### Candidate 3: Amount-Bin Strategy Grid

Goal: test whether the current quantile bins are causing unstable thresholds.

Compare:

| Bin Strategy | Boundaries |
|---|---|
| `quantile_50_80_95` | existing Phase 3.1 quantile bins |
| `fixed_business_amount` | `[0, 50, 150, 500, 2000, inf]` |
| `quantile_60_85_97` | alternative quantile bins |

Policy name:

```text
level4_bin_strategy_grid
```

### Candidate 4: Modified Expected-Cost Diagnostic

This is optional and diagnostic only.

Original formula is not amount-dynamic:

```text
C_FN = beta * TransactionAmt
C_FP = alpha * TransactionAmt
threshold = alpha / (alpha + beta)
```

To make expected cost genuinely transaction-dependent, use a modified business-cost assumption:

```text
C_FP = fixed_review_cost + alpha * TransactionAmt
C_FN = beta * TransactionAmt
```

Then:

```text
flag if (1 - p) * C_FP < p * C_FN
```

This candidate must be labeled:

```text
diagnostic_modified_cost_model
```

and must not replace the main Phase 3.1 cost definition.

## Selection Rules

### Per-Cost Best Candidate

For each Cost-A/B/C:

1. Tune all candidate hyperparameters on validation.
2. Select candidate with lowest validation Total Cost.
3. Tie-break by:
   - lower FP Cost;
   - higher fraud recall;
   - higher fraud precision;
   - simpler policy priority:

```text
global < shrunk < precision_guard < bin_strategy_grid < diagnostic
```

4. Apply selected candidate to test.

### Robust Candidate Summary

Also produce a robust summary row:

```text
policy = level4_tuned_robust_selector
```

Recommended robust score:

```text
normalized_cost = total_cost / approve_all_cost
score = mean(normalized_cost across Cost-A/B/C)
```

Optional guard:

```text
Cost-A/B Total Cost must not exceed Level 3 by more than 5%
Cost-C must improve over Level 3 or Phase 3.1 Level 4 must remain best
```

The robust row is for discussion; per-cost rows remain the main result.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Candidate grid overfits validation | Keep candidate set small; save all hyperparameters; compare on held-out test once |
| Precision guard reduces recall too much | Report recall/precision trade-off and keep per-cost selected policies |
| Cost-C advantage disappears | Preserve Phase 3.1 Level 4 as reference and report the trade-off honestly |
| Modified expected-cost policy confuses the main cost model | Label it diagnostic and keep it out of the main claim unless explicitly selected with explanation |
| Too many notebooks | Keep 04 as clean implementation; 04b is a tuning notebook; Phase 3.2 remains separate |
