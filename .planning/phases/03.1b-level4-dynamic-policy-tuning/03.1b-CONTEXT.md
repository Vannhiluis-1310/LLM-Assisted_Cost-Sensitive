# Phase 3.1b Context: Level 4 Dynamic Policy Tuning

<domain>
## Phase Boundary

Phase 3.1b is a narrow tuning phase after the first Phase 3.1 dynamic policy results.

The current Level 4 amount-bin dynamic threshold shows a useful first success:

- In Cost-C, Level 4 has the lowest observed Total Cost, about `102,499`, and the highest observed Cost Saving, about `84,716`.
- Fraud recall improved meaningfully, e.g. from about `0.5672` to `0.6557`.
- This is aligned with the main project goal because Cost-C represents a high-FN-cost setting where missing fraud is expensive.

The current weakness is over-blocking:

- In Cost-A and Cost-B, Level 4 can lose slightly to `LightGBM_balanced` / strong supervised baselines on Total Cost.
- Fraud precision drops strongly, e.g. from about `0.3353` to `0.1484`.
- The policy catches more fraud but flags too many legitimate transactions when FP cost is not dominated by FN cost.

Phase 3.1b must improve the Level 4 policy-selection/tuning layer. It must not retrain the supervised risk model and must not start Level 5 LLM hybrid work yet.
</domain>

<decisions>
## Locked Decisions

### Scope

- Keep Phase 1/2/2.1/3/3.1 evidence; do not restart earlier phases.
- Do not change notebook 03 Q-bandit ablation in this phase.
- Do not implement Level 5 MiniLM hybrid policy in this phase.
- Prefer a new notebook `notebooks/04b_dynamic_policy_tuning.ipynb` so notebook 04 remains the clean first Level 3/4 implementation.
- Notebook 04b must consume existing Phase 2/3.1 outputs and may reuse helper logic from notebook 04.

### Main Technical Goal

- Reduce Level 4 over-blocking on Cost-A and Cost-B while preserving the Cost-C improvement as much as possible.
- Treat Phase 3.1b as a validation-tuned decision-policy layer over existing `LightGBM` / strong supervised scores.
- Report improvements conditionally and honestly. The project should claim: dynamic amount-bin thresholding improves cost saving under high-FN-cost settings if the data supports it, not that it uniformly beats every baseline.

### Leakage Controls

- All tuning must use validation only.
- Test must be used only for final reporting after candidate policies are frozen.
- Amount-bin boundaries, threshold grids, precision guards, FP caps, and candidate-selection rules must be saved to metadata.
- Candidate policies must be selected by validation criteria before test metrics are displayed.

### Expected-Cost Correction

- Do not claim a pure expected-cost threshold is amount-dynamic when:

```text
C_FN = TransactionAmt * beta
C_FP = TransactionAmt * alpha
```

- The threshold reduces to:

```text
p > alpha / (alpha + beta)
```

- If Phase 3.1b adds an expected-cost policy, it must be clearly labeled as an alternative cost-model diagnostic, such as:

```text
C_FP = fixed_review_cost + alpha * TransactionAmt
```

or:

```text
beta = beta_by_amount_bin
```

This must be separated from the original reward/cost formulation.
</decisions>

<specifics>
## Candidate Tuning Ideas

MVP candidates:

1. `level4_amount_bin_threshold_v1`  
   Existing Phase 3.1 amount-bin policy, kept as a baseline candidate.

2. `level4_shrunk_amount_bin_threshold`  
   Blend per-bin thresholds toward the Level 3 global threshold:

```text
threshold_final = lambda * threshold_bin + (1 - lambda) * threshold_global
```

Tune `lambda` on validation. This should reduce aggressive per-bin thresholds that cause FP explosions.

3. `level4_precision_guard_threshold`  
   Tune per-bin thresholds with a validation precision floor or FP-cost cap. If no threshold satisfies the guard, fall back to the global threshold or the least-bad threshold.

4. `level4_bin_strategy_grid`  
   Compare quantile bins from Phase 3.1 with fixed amount bins such as:

```text
[0, 50, 150, 500, 2000, inf]
```

and optionally log-amount quantile bins.

Stretch candidates:

5. `level4_expected_cost_fixed_fp_diagnostic`  
   Expected-cost policy under a modified business-cost assumption with a fixed review/lost-sale cost. This is diagnostic and must not overwrite the original cost model claim.

6. `level4_robust_selector`  
   Select a policy that minimizes validation Total Cost subject to:

- Cost-A/B Total Cost no worse than Level 3 by more than a tolerance.
- Cost-C keeps a positive saving versus Level 3 or strong supervised baseline.

## Success Signal

Primary success:

- Cost-C remains best or near-best while Cost-A/B FP Cost and precision improve compared with Phase 3.1 Level 4.

Acceptable success:

- If no candidate beats Level 4 on all costs, produce a clear trade-off table and select different policies per cost config.

Failure mode to report honestly:

- Dynamic amount-bin policy improves high-FN-cost behavior but is not robust under lower-FN-cost settings.
</specifics>
