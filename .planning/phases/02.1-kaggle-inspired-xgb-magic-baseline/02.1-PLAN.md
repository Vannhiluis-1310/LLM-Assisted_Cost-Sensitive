# Phase 2.1 Plan: Kaggle-inspired XGB Magic Baseline

## Objective

Upgrade the Phase 2 supervised baseline by adding a leakage-safe XGBoost/LightGBM magic-style model inspired by Kaggle IEEE-CIS solutions, evaluated with the project's internal time split and cost-sensitive metrics.

## Scope

- Modify `notebooks/02_baselines_cost_metrics.ipynb`.
- Keep notebook-first workflow.
- Add feature engineering functions for train-only count/frequency and group-aggregation features.
- Add one strong baseline named `xgboost_magic_style` or `lightgbm_magic_style`.
- Reuse existing Phase 2 metric, threshold tuning, output, and plotting logic.
- Keep smoke mode as default with `SAMPLE_ROWS = 10000`.

## Out of Scope

- No full FraudSquad 1st-place ensemble reproduction.
- No CatBoost/LGBM/XGB ensemble unless explicitly promoted later.
- No leaderboard post-processing.
- No Kaggle test files.
- No TabNet or FT-Transformer.
- No LLM/table-to-text/embedding/RL implementation.
- No claim of beating Kaggle 1st place.

## Implementation Tasks

1. **Add magic-feature configuration**
   - Add `RUN_MAGIC_BASELINE = True`.
   - Add constants for count columns and aggregation keys.
   - Keep all feature lists explicit and small.

2. **Create train-only feature engineering helpers**
   - `make_group_key(df, cols, output_col)`.
   - `fit_count_encoding(train_df, columns)`.
   - `apply_count_encoding(df, count_maps)`.
   - `fit_group_amount_stats(train_df, group_cols)`.
   - `apply_group_amount_stats(df, stats_maps)`.
   - `add_magic_features_train_valid_test(train_df, validation_df, test_df)`.

3. **Enforce leakage safety**
   - Count/frequency maps are computed from train only.
   - Aggregation maps are computed from train only.
   - Unknown validation/test categories map to `0` count and train global median/mean fallback for stats.
   - No `isFraud` or model score is used in feature engineering.
   - No operation computes group stats on concatenated train+validation+test.

4. **Build magic feature matrices**
   - Start from existing `train_X`, `validation_X`, `test_X`.
   - Append magic-derived numeric features.
   - Keep existing `TransactionAmt` and time-derived features.
   - Save a feature audit table to `results/magic_feature_policy.csv`.

5. **Train magic-style baseline**
   - Prefer `XGBClassifier` with `tree_method="hist"` and `scale_pos_weight`.
   - If XGBoost unavailable, use LightGBM with class weighting.
   - If both unavailable, skip magic model with a clear notebook message rather than failing the whole notebook.
   - Use smoke-friendly parameters when `SAMPLE_ROWS` is not `None`.

6. **Integrate with existing evaluation**
   - Add magic model scores to `model_scores`.
   - Reuse existing threshold tuning loop for all cost configs.
   - Ensure `baseline_metrics.csv`, `threshold_tuning.csv`, `confusion_matrices.csv`, and figures include the magic-style baseline.

7. **Add report note cell**
   - Explain that Kaggle 1st place is external SOTA/reference.
   - Explain that internal results are not directly comparable to public/private leaderboard scores because the project uses a different split and cost-sensitive objective.
   - Explicitly avoid claiming improvement over Kaggle 1st place.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Accidental leakage from full-dataset aggregation | Only fit maps on train, add audit comments and verification checks |
| Scope creep into full Kaggle 1st place reproduction | Keep one magic-style model only; treat FraudSquad as external SOTA |
| Local CPU/RAM pressure | Keep smoke mode default and use histogram/tree parameters |
| XGBoost unavailable in Colab/local | Fallback to LightGBM, otherwise skip magic model with clear message |
| Reviewer compares internal AUC to Kaggle leaderboard AUC | Add report note explaining different split/objective and external reference status |

## Threat Model

- Do not upload transaction data to external services.
- Do not use Kaggle credentials or hidden test artifacts in modeling.
- Do not use target label, model predictions, validation/test labels, or future rows in feature engineering.
- Do not present leaderboard scores as directly comparable to internal cost-sensitive results.
